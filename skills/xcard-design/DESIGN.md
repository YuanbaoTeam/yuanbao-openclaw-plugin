# XCard 视觉设计方法

本文件把通用 UI 审美方法约束到元宝移动端 XCard。实现时仍以
`xcard-generator/assets/yuanbao/tokens.json` 和当前 Catalog 为准。

## 默认方向：Apple 式克制

借鉴 Apple 产品界面的设计判断，而不是复制某个系统页面：

- **Clarity**：信息和操作名称直接，文本层级一眼可读，不使用装饰性文案。
- **Deference**：内容是主角，容器和控件退后；能靠留白解决就不加底色或边框。
- **Depth**：只用轻微表面差、分组和状态变化表达层级，不堆叠阴影或伪 3D。
- **Precision**：对齐、间距、圆角、图标尺寸和文本基线保持一致。
- **Calm color**：大面积使用中性表面，品牌色只落在主操作、选择和关键状态。
- **Direct manipulation**：操作后在原位置即时反馈；持续交互卡保持结构稳定。

映射到元宝 XCard：

- 使用元宝 typography variant 和语义色，不指定系统字体或仿造 UIKit/SwiftUI 控件。
- 使用 `cardCornerRadius`、标准 Button/Choice/Input 外观，不自行拼装“苹果控件”。
- XCard 不支持的 blur、material、任意渐变、任意阴影和动画直接舍弃，不做低质量模拟。
- 保留元宝品牌绿色和宿主交互习惯；“接近 Apple”不能覆盖宿主设计系统。
- 普通卡片采用紧凑标题而非页面级超大标题，避免把移动端卡片做成设置页截图。

## 视觉系统

### 层级

只使用三层信息层级：

- **主层**：卡片目标、关键结果或当前状态；首屏第一眼必须找到。
- **辅层**：完成判断所需的数据、选项或解释。
- **弱层**：来源、时间、提示、补充条件；使用 caption/弱文本色，不与主层竞争。

同一层级不要同时用字号、粗细、颜色、底色四种方式强调。通常选择其中一到两种。
模糊或眯眼观察时，应先看到主层和主操作，再看到分组，最后才是辅助文字。

### 间距与节奏

- 以 4dp 为细粒度、8dp 为常规节奏；优先使用 4、8、12、16、24、32。
- 组件内部通常 4–8；同组内容 8–12；主区块之间 16–24。
- Card 内容区遵循元宝 `cardPadding`，不要层层重复 padding。
- 相关内容的距离必须小于它们与下一组的距离。
- 连续三个以上相同间距通常会显得机械，应通过分组间距形成节奏。

### 排版

- 标题优先 `h4/h5`，关键数字可使用更高层级；普通说明使用 `body`，辅助信息使用 `caption`。
- 一张普通卡尽量不超过三个明显字号层级。
- 标题控制在两行内，按钮和状态标签保持一行；长说明先改写，再考虑截断。
- 数值与单位、日期与星期、价格与操作属于稳定关系，避免拆到窄列两端。
- 不用全大写、连续感叹号、装饰符号或 emoji 代替真正的信息层级。

### 色彩与表面

- 默认使用元宝语义 token，保证 light/dark 一致；品牌色只强调关键状态或主操作。
- 功能色只表达对应语义：成功、警告、错误、信息，不能仅为“更鲜艳”使用。
- 一个表面选择一种主要分隔方式：留白、轻底色或分割线。不要同时叠加重底色、边框和阴影。
- 避免每个区块都加 `containerColor`；大多数分组应由间距和排版完成。
- 同屏彩色强调通常不超过两类，避免标签、按钮、标题各用一种抢眼颜色。

### 交互

- 每个逻辑区最多一个主操作。多个等权选择应使用选择组件，而不是一排主按钮。
- 次操作使用较弱的 variant 或文本层级；危险操作只在确有风险时使用警示语义。
- 操作标签写结果而非控件动作，例如“选择周五”“确认订单”，避免笼统的“点击这里”。
- 交互后优先原位更新状态；保持标题、棋盘、列表等主体位置稳定，减少视觉跳动。

## 场景构图

### 先选择交互模式

美观首先来自正确的任务模式，而不是装饰。参考元宝官方模板时，优先按下面的决策选择
Catalog 组件，再调整层级和视觉：

- 多张图片或多个并列主题供浏览：`Pager + DotIndicator`。
- 图片、名称、标签、描述共同参与判断的富选项：`ChoiceGroup`。
- 简短且固定的文字枚举：`ChoicePicker`。
- 数量增减：`Stepper`。
- 选择日期、门店、套餐等对象，并联动替换整块详情：`ItemPicker + Switcher`。
- 动态重复的数据：`List`，不要手写一串近似组件。
- 多步骤澄清或问卷：一屏一题，并提供进度、前后导航和最终提交。
- 默认、选中、售罄、完成等状态差异：`ConditionView` 或 `Visibility`，保持外层结构稳定。
- 纯信息摘要：允许没有按钮，不为“完整”强加 CTA。

若具体组件在当前 Catalog 中不存在，以 `xcard-generator` 查到的能力为准并降级；不得根据
模板名称臆造组件。默认只保留一个明确主操作；多个等权目标应先变成选择，再统一确认。

### 官方模板的通用骨架

多数任务卡按“eyebrow/类别提示 → 主标题 → 一句弱说明 → 主内容 → 操作区”组织，但这只是
信息顺序，不是必须全部出现的固定壳：

- eyebrow 只用于提供有效上下文；没有类别、时间或来源信息时直接省略。
- 主标题回答“这张卡是什么”，尽量一行，最多两行。
- 弱说明只补充任务条件，不复述标题。
- 主内容承担唯一视觉焦点；图片、指标、选项和表单不能同时争抢注意力。
- 两个操作时，次操作使用 `default`，主操作使用 `primary`；不得放两个同权重主按钮。
- 官方模板常见节奏是外层 16、卡内 12、行内 8–10、文字内部 2–6；具体值仍须映射到
  Catalog/token，不能把这些观察写成任意 style 值。
- 主卡片可使用较大的标准圆角，图片和标签依次更小；不要让所有嵌套层都使用同样圆角。

### 选择与确认

结构：标题/一句任务说明 → 选项 → 主操作或结果。

- 选项很多时使用 ChoiceGroup/List，不把每项都画成高权重按钮。
- 单选可即时提交时不再添加重复的确认按钮。
- 已选态必须明显，但不能让所有未选项看起来禁用。
- 富选项让整行成为点击面：固定尺寸图片辅助识别，标题为主层，描述为弱层，选择状态固定在
  行尾；各行图片比例和文字位置必须一致。
- 图片只有在帮助识别或比较时才加入；纯文字选择不为“丰富”虚构配图。
- 带标签的选项中，标签紧贴标题并保持弱背景；标签不能比选项名称更醒目。
- 选择后再提交的任务，把确认操作放在列表之后；不要让每个选项都带一个主按钮。

### 图片与内容轮播

结构：标题/浏览提示 → 单个大画面 → 页码反馈。

- 多图或多主题优先使用 `Pager + DotIndicator`，不纵向堆成长图文页。
- 每页只突出一个主题，并保持图片比例、圆角、标题和描述位置一致。
- 文字覆盖图片时必须保证对比度；renderer 无可靠遮罩能力时，把文字移到图片下方。
- 提示用户可横滑，但不要同时堆叠圆点、页码和冗长操作说明。
- 轮播用于浏览，不适合承载必须逐项确认的表单步骤。

### 对象切换与联动详情

结构：任务标题 → `ItemPicker` → 随选择联动的详情。

- 日期、门店、套餐等选项可横向滚动，不为塞进一行而压缩到难读。
- 当前项使用清晰高对比状态，未选项保持可点击，不能看起来像禁用。
- 用 `Switcher` 更新完整详情，标题、Picker 和整体尺寸尽量稳定。
- 不把对象切换误做成一组提交按钮；切换和最终确认是两个不同动作。

### 多步骤澄清与问卷

结构：当前问题 → 选项/输入 → 上一步、进度、下一步 → 最终提交。

- 一屏一题，避免把全部问题纵向展开成超长表单。
- 问题本身就是当前标题，不再增加重复的卡片大标题。
- 纯文字选项可用通栏列表；序号、正文和选择状态保持固定位置。
- “其他”输入应嵌入对应选项附近，不放到无关的卡片底部。
- 单选使用互斥语义，多选使用多选语义；不要仅靠自绘图标模拟状态。
- 中间步骤显示前后导航和明确进度，只有最后一步出现最终提交。
- 提交后的摘要或完成态通过稳定的条件分支呈现，不重建一张视觉无关的新卡。

### 天气、日程与数据摘要

结构：关键结论 → 2–3 个核心指标 → 可选详情/操作。

- 用户先看到“适不适合”“什么时候”“差异是什么”，再看完整数据。
- 七天数据不要让七个日期都成为视觉焦点；突出推荐项，其余保持一致节奏。
- 来源和更新时间放弱层，不占主区块。

### 持续交互与原位更新

结构：当前状态 → 核心交互区域 → 操作反馈或下一步。

- 适用于游戏、协作选择、进度处理、连续配置等需要多次操作同一卡片的任务。
- 核心任务区域是视觉焦点；标题、说明和辅助操作降低权重。
- 每次更新尽量保持主体 id、尺寸、位置和阅读顺序稳定，只更新发生变化的数据与状态。
- 当前状态、可执行操作和最近一次操作结果必须在卡片内可见，不能依赖聊天文字补充。
- 可点击、已选、不可用、处理中和完成状态必须可辨认，且不能只靠颜色区分。
- 是否允许重复操作属于业务交互语义；视觉设计必须与 `once`、`perRevision` 等实际模式一致。

### 表单与配置

结构：任务标题 → 分组字段 → 单一提交操作。

- 标签靠近字段，帮助文字弱化；必填、错误和禁用状态使用一致规则。
- 长表单拆步或分组，不把所有输入放进一个无节奏的 Column。
- 提交按钮在阅读顺序末端，不能与普通选项争抢层级。
- 商品配置先展示图片、名称和当前配置摘要；固定规格用 `ChoicePicker`，数量用 `Stepper`。
- 每组规格只有一个短标题，选中项使用一致的高对比状态；不要为每个规格手写 Button。
- 售罄、冲突或不可选组合必须同时有文字/状态提示和禁用表现，不能只变灰。

### 列表、商品与门店

结构：标题/筛选摘要 → 重复项 → 当前选择或主操作。

- 行内只保留判断所需字段；次要详情进入弱层或后续页面。
- 图片、名称、关键指标和操作保持固定关系，避免每行布局不同。
- 列表项主要靠留白或轻分割，不把每一行嵌套成重 Card。

### 状态与结果

结构：状态结论 → 关键结果 → 下一步。

- 成功、失败、空态要有明确文字，不只靠颜色或图标。
- 完成态减少可交互元素；仍可继续操作的 `perRevision` 卡片应明确下一步。
- 错误信息说明用户能做什么，不展示内部错误码作为主内容。

## 常见“AI 卡片味”

发现以下模式时优先做减法：

- 所有内容都被圆角底色包住。
- 每行都有图标、标签和分割线，但没有明确焦点。
- 标题、副标题、说明重复表达同一件事。
- 多个同样醒目的主按钮并排。
- 固定的“标题 + 灰色说明 + 一串卡片 + 大按钮”被用于所有场景。
- 为显得丰富而虚构图片、渐变、统计指标或营销文案。
- 使用过多近似的间距、灰色和字号，整体仍没有层级。
